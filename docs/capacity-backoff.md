# 明确容量拒绝的短退避

本机制处理上游明确表示“暂时没有模型容量”的拒绝，不把所有 HTTP 429 当成容量问题。
`turn_rate_limit_exceeded` 只有与有界、固定前缀 `Codex is at capacity` 同时出现于
HTTP 429 的错误字段中才识别为容量拒绝；普通 turn-rate limit、鉴权、参数和余额拒绝
保留原有保护。已有显式模型容量 code 的 400/429/503 合同保持兼容。

## 行为

- 限制身份是 provider、具体 credential、映射后的 upstream model，不扩散到账号组、
  其他账号或其他模型；身份不含 API Key/token。
- 使用独立、有界的进程内状态，默认连续拒绝退避为 **2、4、8、15 秒，之后封顶 15 秒**。
  明确上游 `Retry-After` 作为最低等待时间，不受 15 秒上限裁短；也不缩短尚未结束的限制。
- 容量拒绝不修改 `enabled`，不推进普通分钟级熔断，不写持久化模型冷却，也不降低
  账号健康、AIMD 或软排序分。实际请求的错误与发送次数仍保留在审计中。
- 退避到期直接允许正常业务请求，不需要后台生成探测、半开两次成功或重启程序。
  只有完整请求/流成功才清除对应退避等级；旧在途成功不能清除更新的容量拒绝。
- 退避只在真实发送前拦截，不从路由候选表中剔除该账号，因此不会把容量拒绝变为
  `authorized_candidates_unavailable`。本地拒绝保留上游 status/code/message 和剩余
  `Retry-After`，不计新上游发送，不推进退避级别或再次延长截止时间。

## 与请求恢复等待的关系

开启 [恢复等待](request-recovery-wait.md) 时，由外层请求 owner 保留同一请求，遵守
本地容量退避和上游提示后重新准入。明确容量拒绝可以持续恢复，不受普通 6 次执行
上限截断；每次真实拒绝只增加一个资格，真实发送和审计计数不回退。工具声明可使用
这个明确拒绝例外，未知执行、已移交流、媒体创建不适用。

关闭恢复等待时，继续使用下述旧有限自动重试；两套机制不会叠加发送。

## 关闭恢复等待时的有限自动重试

沿用 `RequestBudget` 的安全重放分类、发送次数上限、原始 deadline 和响应移交边界。
安全请求在未移交响应、预算和完整等待时间允许时，最多获得**整个逻辑请求共一次**
容量自动重试许可。首次非黏性流请求仅额外开放这个容量特例，不开放普通网络错误重试。
adapter 显式禁止重放、携带工具/工具历史、媒体创建、已移交流等场景不借此重新发送。
原重试累计等待预算不足时直接返回上游错误，不裁短等待，不新建 deadline。

不主动换模型，不增加账号授权，不增加付费健康探测；并发自适应不属于本次改动。
状态最多保留 8192 个身份，不淘汰仍有效的限制或在途 lease；满载时拒绝新增身份的准入，
已到期且无在途调用的记录可回收。取消通过既有 Drop 生命周期释放 lease，无新增后台任务。

本机制不修改旧实例的内存或历史持久化限流记录；新源码必须进入后续新包才影响用户程序。
自动验证使用虚拟时钟、loopback 合成 Responses JSON/SSE 与隔离 Local 数据库，不能代替
真实供应商、EXE 打包或人工验收。具体测试回执见本轮进度记录。
