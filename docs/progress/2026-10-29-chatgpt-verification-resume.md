# ChatGPT Web 人工验证续接与退出判断

## 问题和边界

用户正常完成网页登录，不等于 Gateway 已取得 `/api/auth/session` 的会话材料。
此前保留现场的请求返回过 HTTP 403 和 `cf-mitigated: challenge`，不能据此判断用户
没有登录、账号失效或指定模型没有权限。本轮没有重新读取真实会话，也没有重放真实模型请求。

现有导入在明确要求浏览器验证后立即结束事务、关闭浏览器并删除专用 profile。
错误分类虽然准确，但用户没有继续正常验证的入口。这是本轮新增恢复步骤所修复的流程缺口。

## 同一事务中的一次人工续接

1. 保留原有正常登录方式：专用 profile；人工登录阶段没有 CDP 或自动化参数。
2. 关窗后读取会话。只有明确的 `session_verification_required` 进入恢复步骤，普通 403 不进入。
3. 先安全关闭读取窗口，暂时保留该事务的 profile，停止会话请求并显示“打开验证窗口”。
4. 只有用户点击才打开同一 profile 的正常浏览器窗口。目标固定为官方会话页面，未启用 CDP；
   用户正常完成官网验证后关闭窗口，不需要复制页面内容或把任何秘密发到聊天中。
5. 仅执行一轮新的捕获；再次要求验证则停止，不再次开窗，不更换账号、模型、代理或出口。
6. 仅取得并校验材料后才显示“已读取账号”。模型目录失败仍不得丢弃已经读取的账号。

人工等待最多两分钟，但包含在原来的总事务预算内，不是额外增加两分钟。
Node 工作/硬停止和 Rust supervisor 仍分别使用 205/220/225 秒；最终清理预算仍为 14 秒。
取消、组件卸载、权限/服务商切换、请求断开和超时仍由原 supervisor 回收自有进程树与 scratch。
没有把 profile 变成脱离 owner 的长期后台数据，也没有增加跨应用重启恢复合同。

## 状态通道与权限

状态与继续操作复用管理接口的鉴权、敏感信息授权、直接 loopback、已保存 provider 和 revision 校验。
进行中的请求还绑定管理 token fingerprint、provider、原 revision 和 requestId。
前端只收到固定阶段，不收到 profile 路径、CDP 地址、Cookie、token 或页面响应。

状态通道在 supervisor-owned scratch 中使用五个固定、不可变的空阶段标记和一个
`create_new` 的空同意标记。Windows 实测曾出现替换正在被读取的状态文件返回 `EPERM`；
因此不采用覆盖/rename 的单一状态文件。标记顺序、类型和尺寸固定，不能传任意命令、URL 或请求头。
迟到的 verify 响应不能把 UI 从后续“正在读取”回退到等待人工关窗。

## 原生退出判断

仅合成 loopback 的追踪证明：`Browser.close` 已确认，taskkill 已终止自有 Chrome root，
系统只读存活检查返回 `ESRCH` 时，Node 的 `exit` 回调仍可能延后。
旧逻辑继续仅等待回调，并把已经不存在的进程误认为活进程，导致 `cleanupPending`
或阻止 profile 进入人工验证阶段。

现在清理同时参考已登记 child 的退出状态和系统明确的 PID 不存在结果。只有明确 `ESRCH`
才视为不存在；未知错误、权限拒绝和仍然存活均保守处理，不能据此删除目录。
没有延长原有单阶段或总清理时限，没有取消“已知活 owner 不得删除 profile”的保护，
也没有把 taskkill 的整体退出码当成浏览器根进程是否退出的唯一证据。

进一步的阶段追踪还复现了另一处错误：taskkill helper 等待回调超时，但浏览器根进程已经
退出时，旧逻辑把 helper 失败永久标为清理失败，未再核实目标。现在 helper 的成功或失败
都必须经过相同的目标退出检查；确认不存在才可继续，目标仍在或检查结果不明仍停止清理。
该回归先失败后通过，见 `cleanup-helper-red` 和 `cleanup-helper-green` 回执。

原生测试额外连接的 fixture CDP owner 会先在仍启用请求拦截时转到 `about:blank` 并断开，
避免断开 fixture 后恢复真实官网请求。此调整没有解决退出回调延迟，不能作为其根因解释。

四阶段原生夹具曾把整轮工作限制为 45 秒，而计时证明第二次 capture 约第 35 秒才就绪。
原生恢复测试现直接使用生产既有的 205 秒工作预算；Cookie 测试的正常关窗等待也与生产
既有 180 秒一致。没有放宽生产超时或清理预算。每个 owned root 必须通过独立系统检查
证明 PID 已不存在，不能只凭可能迟到的 Node 退出字段断言回收成功。
