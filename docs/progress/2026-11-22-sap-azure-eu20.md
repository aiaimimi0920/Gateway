# SAP AI Core：Azure EU20 Chat 部署地址

2026-11-22 完成源码接入及本地模拟验收。SAP [Developer Center 教程第 6 步](https://developers.sap.com/tutorials/dev-garage-error-resolution-ai-adapter) 列出 `https://api.ai.prod-eu20.westeurope.azure.ml.hana.ondemand.com` 作为 AI Core 地址。教程使用 Orchestration，只证明该 API origin 有官方依据；显式 Chat 部署仍按 SAP [OpenAI 合同](https://github.com/SAP-docs/sap-artificial-intelligence/blob/8fc8e1de82fcb34766e1867e83640efc4d0bb93e/docs/sap-ai-core/generativeAI/openai-490f55d.md) 使用租户返回的 `deploymentUrl`，本轮没有实现 Orchestration。

## 实现与回归

- Gateway 与控制台都接受这个精确 Azure EU20 origin，保留已有 AWS hostname 模式。部署 URL 仍需使用完整 `/v2/inference/deployments/<id>` 路径；其他 Azure 地区、GCP、仿冒域名、端口、用户信息、乱改路径、查询或片段不在支持范围。无新增配置或数据迁移。
- Azure Service Key 可使用带 `/v2` 的 `AI_API_URL`；AWS 和 Azure 的 Key 不可跨 origin 绑定。通过管理 CAS 尝试 Keep 原 AWS 凭据改绑 Azure，被 `secret_keep_destination_changed` 拒绝，配置和修订未变。XSUAA、mTLS、重定向与凭据隔离规则没有放宽。
- 受保护的目录查询只返回匹配 Key origin 的 Azure Chat 部署，排除模拟返回的 AWS 部署。前端覆盖了 AWS／Azure 的空池创建和 Key 表单提交，均不自动探测或生成。
- Local 公共 `/v1/chat/completions` 各完成一次 JSON 和 SSE；循环内只向本地模拟上游发送两次生成，共用一次合成 Token 交换。读回两条完成审计，均归属预期账号与凭据，每条 5 tokens；夹具的两条 Gateway 预付消息扣减至零。这不是 SAP 实际用量或扣费。
