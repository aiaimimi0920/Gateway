Files
Upload files once with the Luma Agents Files API and reference them across many image and video generations by file_id.
The Files API lets you upload an image or video once and reference it from many generations by its
file_id
— instead of re-sending a URL or re-encoding base64 on every request. Uploaded files are moderated once at ingest, so referencing one later skips the per-request fetch/decode and the moderation round-trip.
Note
Files belong to your API account — they’re scoped to your key, and you are
responsible for access control among your own end users.
When to use a file
Section titled “When to use a file”
A
file_id
is one of the media reference shapes accepted anywhere
ImageRef
is —
source
,
image_ref[]
,
video.start_frame
/
end_frame
, and
video.keyframes

You have
Use
Media you’ll reference more than once
file_id
(upload it)
A one-off, publicly reachable URL
url
Small bytes you already hold in memory
data
(base64)
The output of a prior generation
generation_id
Uploading is worth it when the same asset feeds several generations, when the bytes aren’t publicly hosted, or when you want moderation to happen up front rather than on the generation’s critical path.

File lifecycle
Section titled “File lifecycle”
After upload, ingest and moderation run asynchronously. Poll
GET /v1/files/{file_id}
until the file reaches a terminal state:
State
Meaning
pending
Bytes received; ingest/moderation in progress. Not yet referenceable.
ready
Available — reference it from a generation by
file_id
.
failed
Ingest or moderation rejected the file; see
failure_reason
.
deleted
Deleted; can no longer be referenced, and
GET
returns
404
.
A file must be
ready
before a generation can reference it. Referencing a
pending
,
failed
, or
deleted
file is rejected.

A file is independent of the generations that reference it by
file_id
; removing a generation never removes the file. Delete the file itself with
DELETE /v1/files/{file_id}
.
A deleted file disappears from
GET
(
404
) and list right away, and new generations can no longer reference it. Its stored bytes are not removed during the request. Where file retention is enabled for your API client, a background job then permanently deletes them, keeping stored bytes another live artifact still references; otherwise the bytes stay stored until a Luma operator purges them. A
failed
file, or a file past its
expires_at
, can also be deleted until its stored bytes have been purged. Re-issuing
DELETE
is idempotent: it returns
204
until the stored bytes have been purged, and
404
(
FILE.NOT_FOUND
) after that.
Fields
Section titled “Fields”
Field
Notes
purpose
input
(a primary subject, e.g. an edit source) or
reference
(style/content guidance). Defaults to
input
.
mime_type
Required in the presigned flow; sniffed from the bytes in the inline flow.
size_bytes
Required (and enforced) in the presigned flow. Up to 5 GiB (the storage single-
PUT
ceiling).
expires_at
Optional TTL; once it passes,
GET
and list hide the file and generations can no longer reference it. Where file retention is enabled for your API client, its stored bytes are then permanently deleted by a background job, keeping stored bytes another live artifact still references.
user_id
Optional opaque end-user tag for abuse attribution — mirrors
user_id
on
generations
. Echoed back unchanged.
