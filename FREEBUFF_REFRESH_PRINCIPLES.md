# Freebuff Refresh Principles

## Purpose

This document is for implementing native Freebuff/Codebuff support inside the Rust gateway.

It focuses on one narrow topic:

- what "refresh" means in the Freebuff stack
- which layer can be renewed
- which layer cannot be renewed
- how the gateway should react to expiry or rejection
- which upstream files are the most important references

This document is intentionally written for another coding agent or engineer. It is not a product overview.

## Executive Summary

There are **three different objects** that are easy to confuse:

1. `auth_code`
2. `authToken` / `sessionToken`
3. `free session` identified by `instanceId`

Only the third item is re-acquired by `POST /api/v1/freebuff/session`.

That endpoint is **not** an OAuth-style refresh endpoint and **not** a login-token refresh endpoint.

The correct model is:

- `auth_code` is a short-lived browser-to-CLI login bridge
- `authToken` is a database-backed session credential used as the actual bearer token
- `instanceId` is a free-mode admission token for the waiting-room gate

The gateway should therefore implement **two separate runtime layers**:

- credential validity for `authToken`
- free-session validity for `instanceId`

Do **not** merge them into one "refresh token" abstraction.

## Terminology

### `auth_code`

- Generated by `POST /api/auth/cli/code`
- Intended to bridge an already-authenticated browser session to a CLI fingerprint
- Valid for a short time only
- Not used for normal inference after login completes

### `authToken` / `sessionToken`

- Returned to the CLI by `GET /api/auth/cli/status`
- Stored in `~/.config/manicode/credentials.json`
- Used as `Authorization: Bearer <token>` for normal API calls
- Backed by the server-side `session` table

### `free session`

- Managed by `POST/GET/DELETE /api/v1/freebuff/session`
- Represents admission to free-mode traffic
- Identified by `instanceId`
- Required for free-mode chat requests as `codebuff_metadata.freebuff_instance_id`

## What The Upstream Code Actually Does

### 1. `auth_code` is short-lived and only starts the login flow

The Freebuff/Codebuff service generates an `auth_code` with a 1 hour expiry:

- `web/src/app/api/auth/cli/code/route.ts`

Important detail:

- This code is only a login bridge.
- It is not the bearer token used for later API requests.

### 2. The CLI bearer token is the server session token

The login status route returns:

- `user.authToken`

That value is read directly from:

- `schema.session.sessionToken`

and only when:

- `schema.session.expires > now()`

Relevant files:

- `web/src/app/api/auth/cli/status/route.ts`
- `packages/internal/src/db/schema.ts`
- `web/src/util/auth.ts`

This means the CLI credential is a **server-managed session token**, not a permanent API key.

### 3. Session max age is 30 days in source, but should not be treated as guaranteed availability

The current repository config uses:

- `SESSION_MAX_AGE_SECONDS = 30 * 24 * 60 * 60`

and applies it via NextAuth database sessions.

Relevant files:

- `common/src/constants/limits.ts`
- `web/src/app/api/auth/[...nextauth]/auth-options.ts`

This is a configuration default, not a reliability guarantee.

The gateway must assume the token can still be invalidated earlier due to:

- logout
- server-side deletion
- deployment differences between Freebuff and Codebuff
- upstream policy changes
- account state changes

### 4. Free-mode access is separately gated by a waiting-room session

The upstream repository documents a free waiting-room layer:

- `POST /api/v1/freebuff/session`
- `GET /api/v1/freebuff/session`
- `DELETE /api/v1/freebuff/session`

Important defaults from the current docs:

- session length: 1 hour
- grace window: 30 minutes
- free-mode chat requests must include `freebuff_instance_id`

Relevant files:

- `docs/freebuff-waiting-room.md`
- `web/src/app/api/v1/chat/completions/_post.ts`

This gate is **independent** from login.

## The Most Important Implementation Rule

`POST /api/v1/freebuff/session` does **not** refresh `authToken`.

It only re-creates or rotates the **free-mode admission session**.

This distinction is the single most important design constraint for the gateway.

## Refresh Matrix

### Can `auth_code` be refreshed?

Not in the sense the gateway cares about.

- A new `auth_code` can be requested by repeating the login-bridge flow.
- The gateway should not implement this.
- Credential acquisition belongs to an external onboarding or operator workflow.

### Can `authToken` be refreshed by the gateway?

No refresh-token mechanism was found for the Freebuff CLI auth path.

The repository does contain explicit refresh-token logic for:

- Claude OAuth
- ChatGPT OAuth

but not for the main Freebuff CLI credential.

Therefore the gateway should treat Freebuff `authToken` as:

- externally provisioned
- replaceable
- invalidatable
- not self-refreshable

### Can the free session be refreshed?

Partially, but "refresh" is the wrong word.

The gateway can:

- create a free session
- poll free-session state
- rejoin the queue after expiry
- rotate to a new `instanceId`

The gateway cannot:

- extend the original 1 hour active window by calling `POST /session`
- convert an invalid `authToken` into a valid one

## Critical Misconception To Avoid

Do **not** model this as:

- login token expires every hour
- call `POST /api/v1/freebuff/session` to renew token

That model is wrong.

The correct model is:

- login token may remain valid for some period, often configured for up to 30 days
- free-mode admission expires around every hour
- after free-session expiry, the client must rejoin the waiting room
- if the login token itself is rejected, only external re-login can recover it

## Exact Semantics Of `POST /api/v1/freebuff/session`

According to `docs/freebuff-waiting-room.md`, the current semantics are:

- no existing row: create queued session with a fresh `instanceId`
- existing queued row: rotate `instanceId`, keep queue position
- existing active and unexpired row: rotate `instanceId`, preserve current active session
- existing active but expired row: reset to queued with a new queue timestamp

This produces two very important constraints:

1. Calling `POST /session` while already active does **not** extend the session expiry.
2. Calling `POST /session` after expiry does **not** instantly restore an active seat; it may place the caller back into `queued`.

Therefore a timer that blindly calls `POST /session` every hour is **not** a reliable "keepalive".

## Grace Window Semantics

The waiting-room design includes a drain window:

- after `expiresAt`, but before `expiresAt + grace`
- gate result is effectively "draining"
- in-flight work may finish
- the client is expected to stop accepting new prompts

This means the gateway should distinguish:

- active free session
- draining free session
- expired free session

Draining is not the same as healthy active.

The gateway should not use the grace period to start new user requests unless product requirements explicitly allow that behavior.

## Recommended Gateway Runtime Model

### Layer A: Credential Runtime

Keyed by provider credential or account.

Tracks:

- bearer token presence
- last successful auth check
- invalid/401 state
- cooldown or quarantine state after auth rejection

Rules:

- if any authenticated endpoint returns `401`, mark the credential invalid
- do not try `POST /api/v1/freebuff/session` as a recovery for `401`
- require external credential replacement

### Layer B: Free Session Runtime

Also keyed by provider credential or account.

Tracks:

- `none`
- `queued`
- `active`
- `draining`
- `superseded`
- `expired`

Stores at minimum:

- `instanceId`
- `admittedAt`
- `expiresAt`
- `graceEndsAt`
- queue metadata if available

Rules:

- free-mode requests require a valid `instanceId`
- when absent, call `POST /api/v1/freebuff/session`
- when queued, poll `GET /api/v1/freebuff/session`
- when active, inject `codebuff_metadata.freebuff_instance_id`
- when superseded or expired, re-run `POST /api/v1/freebuff/session`

## Error Handling Rules

These rules should be hard-coded in the adapter logic.

### `401 Unauthorized`

Meaning:

- the bearer credential itself is invalid or expired

Gateway action:

- mark credential invalid
- stop trying free-session recovery
- surface operator-visible credential failure

### `426 freebuff_update_required`

Meaning:

- request did not include `freebuff_instance_id`

Gateway action:

- treat as local adapter bug or missing free-session bootstrap
- create or reload the free session

### `428 waiting_room_required`

Meaning:

- no free-session row exists

Gateway action:

- call `POST /api/v1/freebuff/session`

### `429 waiting_room_queued`

Meaning:

- the user is queued and not yet active

Gateway action:

- poll `GET /api/v1/freebuff/session`
- do not interpret this as credential expiry

### `409 session_superseded`

Meaning:

- another client rotated the `instanceId`

Gateway action:

- discard the local `instanceId`
- call `POST /api/v1/freebuff/session` again

### `410 session_expired`

Meaning:

- free session passed the hard cutoff

Gateway action:

- discard local free-session state
- call `POST /api/v1/freebuff/session`
- expect possible re-queue, not instant activation

## Request Construction Requirements

For free-mode chat, the gateway should inject all of the following:

- `codebuff_metadata.run_id`
- `codebuff_metadata.cost_mode = "free"`
- `codebuff_metadata.client_id`
- `codebuff_metadata.freebuff_instance_id`

Without `freebuff_instance_id`, the free waiting-room gate may reject the request even if `authToken` is still valid.

## Why The Current Go Proxy Is Incomplete For Long-Lived Freebuff Access

The current local `Freebuff2API` implementation injects:

- `run_id`
- `cost_mode`
- `client_id`

but does **not** implement:

- `POST /api/v1/freebuff/session`
- `GET /api/v1/freebuff/session`
- `freebuff_instance_id` injection
- waiting-room state handling

Relevant local file:

- `C:\Users\Public\nas_home\AI\GameEditor\FreeBuffAPI\server.go`

Observed code path:

- `injectUpstreamMetadata()` adds `run_id`, `cost_mode`, `client_id`
- no waiting-room state is present in the current Go proxy codebase

This is why a token can appear to "work once and then expire quickly" even when the root problem is free-session admission rather than login expiry.

## Recommended Coding Scope For The Rust Gateway

The Rust gateway should implement:

1. direct bearer-token use against Codebuff endpoints
2. explicit free-session state management
3. `instanceId` injection for free-mode requests
4. separate handling for auth failures versus waiting-room failures

The Rust gateway should **not** implement:

1. browser login automation
2. `auth_code` generation as part of the hot path
3. assumed refresh-token logic for Freebuff bearer credentials

## Suggested Implementation Order

1. Implement credential validity checks and 401 handling.
2. Implement free-session bootstrap with `POST /api/v1/freebuff/session`.
3. Implement free-session polling with `GET /api/v1/freebuff/session`.
4. Inject `freebuff_instance_id` into free-mode chat requests.
5. Map `426/428/429/409/410` into local session-state transitions.
6. Only after this, optimize with caching, background refresh, or queue polling strategies.

## Final Guidance For Another AI

If you are implementing Freebuff support in the Rust gateway, follow this rule:

> Treat login credential renewal and free-session re-admission as two different state machines.

If a request fails:

- `401` means "credential problem"
- `426/428/429/409/410` means "free-session problem"

Do not attempt to repair a `401` with `POST /api/v1/freebuff/session`.

Do not assume periodic `POST /api/v1/freebuff/session` calls will keep a free seat alive.

Do not ship a Freebuff adapter without `freebuff_instance_id` support if it is intended to survive beyond a single short-lived happy-path session.
